# Entrega — 13/09/2026

## O que o front precisa

```http
PUT /v1/analyses/{job_id}/disp-status
{ "disp_status": 0 }        // 0 = depreciada · 1 = ativa
```

**Campo único:** `disp_status`. O corpo é `extra="forbid"` — qualquer outra chave
dá 422. Essa rota muda visibilidade e nada mais.

**Resposta 200:** `{ job_id, disp_status, disp_status_updated_at }`

**Erros:** `404 ANALISE_NAO_ENCONTRADA` (inexistente **ou** de outro usuário —
403 confirmaria que existe) · `422` para valor fora de `{0,1}` ou campo extra.

**Idempotente** — mandar `0` duas vezes devolve 200 nas duas, então retry não
precisa de tratamento especial.

**E o front não precisa filtrar nada:** `GET /v1/analyses` passou a esconder as
depreciadas. Depois do PUT a análise já não volta. Para uma tela de lixeira,
`?incluir_depreciadas=true`.

Contrato completo em [`docs/endpoints/disp-status.md`](endpoints/disp-status.md).

### Por que não virou DELETE

Um DELETE levaria junto o `llm_input_payload`, que é a fonte da geração de
Terraform e de qualquer reanálise. Quem excluísse por engano perderia o pacote
que já baixou, sem volta. Assim o usuário tem um mês, e "desfazer" é a mesma
rota com `1`.

O expurgo é `scripts/expurgar_analises.py` (cron), com simulação por padrão.
`disp_status_updated_at` existe porque sem ela "apaga depois de 1 mês" não teria
de quando contar — o primeiro expurgo levaria tudo que já estivesse depreciado.

**Um efeito colateral que descobri testando e vale o front saber:** análise
depreciada agora **libera o relatório** para uma nova análise, mesmo travada em
`PENDING`. O índice de idempotência passou a considerar `disp_status = 1`. Sem
isso o usuário ficava num beco — "excluía" e continuava sem conseguir
reanalisar, sem mensagem nenhuma.
